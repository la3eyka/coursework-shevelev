# Web Performance Analyzer

**Тема курсовой работы:** «Исследование методов оптимизации загрузки веб-страниц: разработка инструмента анализа и рекомендаций».

> **Статус:** проектная спецификация и план реализации. Описанные функции, API и команды запуска — целевая архитектура, а не утверждение, что программа уже написана. По мере разработки README необходимо актуализировать.

## О проекте

Web Performance Analyzer — веб-приложение для автоматизированного исследования скорости загрузки веб-страниц. Пользователь указывает URL страницы, выбирает режим анализа (мобильное или десктопное устройство) и получает численные показатели производительности, перечень обнаруженных проблем и понятные рекомендации по их устранению. Результаты сохраняются, чтобы можно было сравнивать повторные измерения одной страницы.

В основе измерений используется **Google Lighthouse**, запускаемый программно из собственного серверного приложения через **Google Chrome / Chromium**. Самостоятельно разрабатываются интерфейс, серверное API, хранение результатов, обработчик диагностических данных, правила формирования рекомендаций, система приоритетов и сравнение измерений.

**Важно:** инструмент не изменяет анализируемые сайты автоматически. Он измеряет их производительность и предлагает способы оптимизации. Он также не обещает обнаружить каждую причину медленной загрузки.

### Цель курсовой работы

Исследовать методы оптимизации загрузки веб-страниц и разработать программный инструмент, позволяющий автоматически измерять производительность, выявлять типовые проблемы и формировать обоснованные рекомендации.

### Объект, предмет и гипотеза исследования

- **Объект исследования:** процесс загрузки и отображения веб-страниц в браузере.
- **Предмет исследования:** методы измерения и оптимизации загрузки веб-страниц и способы автоматизации их анализа.
- **Рабочая гипотеза:** применение набора методов оптимизации (изображений, JavaScript, CSS и др.) может уменьшить временные показатели загрузки тестовых страниц, а инструмент на базе Lighthouse способен обнаружить часть соответствующих проблем и помочь определить приоритет исправлений. Гипотеза подлежит экспериментальной проверке, а не принимается заранее как доказанная.

### Задачи курсовой работы

1. Рассмотреть основные этапы загрузки страницы и факторы, влияющие на производительность.
2. Изучить метрики Lighthouse и Core Web Vitals, разграничить лабораторные и пользовательские измерения.
3. Систематизировать методы оптимизации HTML, CSS, JavaScript, изображений и сетевых ресурсов.
4. Разработать архитектуру инструмента анализа и структуру хранения данных.
5. Реализовать запуск Lighthouse и получение машиночитаемого отчёта.
6. Реализовать алгоритм классификации проблем и генерации рекомендаций.
7. Создать интерфейс отображения метрик, истории и сравнения запусков.
8. Провести повторяемые эксперименты на тестовых страницах до и после оптимизации.
9. Проанализировать результаты, ограничения методики и сформулировать выводы.

## Основные возможности

### Обязательный функционал (MVP)

- Ввод URL для проверки и выбор режима `mobile` / `desktop`.
- Проверка формата и допустимости адреса; безопасное ограничение запросов.
- Постановка задания на измерение и отображение состояния (`queued`, `running`, `completed`, `failed`).
- Запуск Lighthouse для одной страницы и получение его JSON-результата.
- Извлечение ключевых метрик: Performance Score, FCP, LCP, Speed Index, TBT, CLS.
- Анализ диагностических аудитов Lighthouse и создание собственных рекомендаций по заданным правилам.
- Группировка рекомендаций по категориям и приоритетам с объяснением причин.
- Сохранение результатов в PostgreSQL.
- История проверок; сравнение двух запусков для одной страницы в одинаковом режиме.
- Базовые автоматические тесты и набор воспроизводимых экспериментов.

### Дополнительный функционал (при наличии времени)

- Экспорт отчётов в PDF, HTML или CSV (для начала достаточно JSON/CSV).
- Графики изменения метрик за несколько запусков.
- Скриншот анализируемой страницы и показ URL проблемных ресурсов.
- Пакетная обработка нескольких URL и фоновая очередь заданий с устойчивым восстановлением.
- Интеграция с PageSpeed Insights API и отдельное отображение доступных полевых данных.
- Дополнительные пользовательские правила и CI-проверки регрессий производительности.

**Не входит в MVP:** авторизация пользователей, JWT/RBAC, Redis, микросервисы, автоматическая правка исходного кода чужого сайта, искусственный интеллект для генерации советов.

## Что анализирует инструмент

| Показатель | О чём говорит | Источник / ограничение |
| --- | --- | --- |
| Performance Score | Сводная оценка Lighthouse, 0–100 | Рассчитывается Lighthouse; зависит от версии и настроек |
| FCP (First Contentful Paint) | Время появления первого содержимого | Лабораторное измерение Lighthouse |
| LCP (Largest Contentful Paint) | Время отображения основного крупного элемента | Лабораторное измерение Lighthouse |
| Speed Index | Скорость визуального заполнения экрана | Лабораторное измерение Lighthouse |
| TBT (Total Blocking Time) | Суммарная блокировка главного потока длинными задачами | Лабораторное измерение Lighthouse, **не равно INP** |
| CLS (Cumulative Layout Shift) | Неожиданные сдвиги макета | Лабораторное значение Lighthouse |
| TTFB (Time to First Byte) | Задержка до получения первого байта HTML | Дополнительная диагностика, если доступна |
| INP (Interaction to Next Paint) | Отзывчивость взаимодействий реальных пользователей | **Не определяется одним обычным запуском Lighthouse при загрузке**; полевые данные — отдельная будущая интеграция |

**Ориентиры Core Web Vitals для реального пользовательского опыта:** LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1 (оценка по 75-му процентилю пользовательских измерений). Эти пороги не следует выдавать за полную замену лабораторной шкалы Lighthouse.

## Методы оптимизации и примеры рекомендаций

| Найденная проблема | Возможная рекомендация | Как проверить эффект |
| --- | --- | --- |
| Большие изображения, неэффективный формат | Сжать изображения; применять WebP/AVIF и подходящие размеры | Сравнить массу ресурсов и LCP |
| Изображения за пределами первого экрана загружаются сразу | Использовать `loading="lazy"` там, где это уместно | Сравнить сетевую нагрузку и метрики загрузки; **не лениво загружать LCP-изображение** |
| Неиспользуемый/тяжёлый JavaScript | Разделить код по маршрутам, применять динамические импорты и удалять неиспользуемые зависимости | Сравнить размер JS и TBT |
| Ресурсы блокируют отрисовку | Убрать ненужные блокирующие скрипты и пересмотреть загрузку критических стилей | Сравнить FCP и LCP |
| Тяжёлые стили или неиспользуемый CSS | Минифицировать и исключить неиспользуемые стили | Сравнить массу CSS и FCP |
| Отсутствует эффективное кэширование статических ресурсов | Настроить подходящие `Cache-Control`/версирование ресурсов | Проверить HTTP-заголовки; холодный и тёплый кэш исследовать отдельно |
| Шрифты вызывают задержки/сдвиги | Настроить загрузку шрифтов, `font-display` и резервы пространства | Сравнить FCP / CLS |
| Долгий ответ сервера | Проверить серверную обработку, запросы к БД, CDN и кеширование | Сравнить TTFB в сопоставимых условиях |

### Собственный алгоритм рекомендаций

1. Получить аудиты и метрики из Lighthouse JSON.
2. Отфильтровать неприменимые/пройденные проверки; отдельно учитывать недоступные показатели.
3. Сопоставить идентификаторы аудитов с собственным справочником правил.
4. Построить рекомендацию: **проблема → доказательство/значение → причина → предлагаемое действие → ожидаемая затрагиваемая метрика**.
5. Присвоить приоритет по прозрачной эвристике: серьёзность проблемы, оценка потенциального влияния (если Lighthouse её предоставляет), уверенность в правиле и сложность исправления.
6. Не выдавать ориентировочную экономию времени за уже измеренное ускорение. Реальный эффект устанавливается повторным тестированием.

Примеры категорий: `images`, `javascript`, `css`, `network`, `fonts`, `rendering`.

## Данные и модель хранения

Минимально необходимы следующие сущности:

- **Analysis** — `id`, `url`, `strategy`, `status`, `createdAt`, `startedAt`, `finishedAt`, `error`, `lighthouseVersion`, `settingsJson`.
- **Metrics** — `analysisId`, `performanceScore`, `fcpMs`, `lcpMs`, `speedIndexMs`, `tbtMs`, `cls`, необязательный `ttfbMs`.
- **Recommendation** — `id`, `analysisId`, `auditId`, `category`, `priority`, `title`, `explanation`, `action`, опциональные данные о предполагаемой экономии.
- **RawReport** — ссылка на сохранённый JSON/HTML-отчёт, если этот формат включён (большие отчёты лучше хранить в отдельной директории, а не дублировать в полях метрик).

## Планируемое REST API

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/health` | Проверка работоспособности API |

### Пример предполагаемого контракта API (не реализован)

Запрос:

```http
POST /api/analyses
Content-Type: application/json

{"url":"https://example.com","strategy":"mobile"}
```

Ответ при принятии задания:

```json
{"id":"sample-analysis-id","status":"queued"}
```

Получение результата:

```http
GET /api/analyses/sample-analysis-id
```

При успешном завершении возвращаются статус `completed`, URL, режим, численные метрики и массив рекомендаций. При ошибке — статус `failed` и описание причины без раскрытия внутренних секретов.

### Интерфейс приложения

1. **Главная:** поле URL, переключатель mobile/desktop, запуск.
2. **Результат:** статус проверки, Performance Score, метрики, список проблем и рекомендаций.
3. **История:** ранее проверенные адреса, дата, режим, сводная оценка.
4. **Сравнение:** два сопоставимых анализа, абсолютные и процентные изменения метрик.

## Требования к безопасности и воспроизводимости

- По умолчанию разрешать только внешние URL с `http:` / `https:`; локальные, частные, link-local и служебные адреса блокировать. Для демонстрационных локальных страниц предусмотреть явное исключение **только в режиме разработки**.
- Проверять конечные адреса перенаправлений и результаты DNS, чтобы не допустить обхода фильтров и SSRF.
- Ограничить число параллельных проверок, время исполнения и размер сохраняемых данных.
- Надёжно завершать запущенный Chrome после анализа, включая случаи ошибок.
- Не запускать произвольные команды из пользовательского ввода и не публиковать приложение без дополнительных мер изоляции браузера.
- Записывать версию Lighthouse, тип устройства/режим и условия испытания; одинаковые настройки необходимы для корректного сравнения.
- Не сравнивать напрямую замеры mobile и desktop, а также лабораторные метрики с полевыми процентилями.

## Развёртывание и установка (план)

**Предварительно установить:** Node.js 22+ (желательно актуальную LTS-версию), npm, Google Chrome, Git, Docker Desktop с работающим Docker Engine.

> Следующие команды описывают создание каркаса; они **не запускают готовый продукт без реализации исходных файлов, скриптов и конфигурации**.

### 1. Создание репозитория и frontend

```bash
mkdir web-performance-analyzer
cd web-performance-analyzer
npm create vite@latest frontend -- --template react-ts
cd frontend
npm install
npm install react-router-dom recharts
cd ..
```

### 2. Создание backend

```bash
mkdir backend
cd backend
npm init -y
npm install fastify @fastify/cors lighthouse chrome-launcher @prisma/client
npm install -D typescript tsx @types/node prisma vitest
npx tsc --init
cd ..
```

После этого необходимо создать маршруты Fastify, модуль Lighthouse, схему Prisma, скрипты `dev` / `build` / `test` в `package.json` и файлы окружения.

### 3. PostgreSQL

Создать `docker-compose.yml` с сервисом `postgres` и постоянным томом. Затем:

```bash
docker compose up -d postgres
```

Команда заработает **только после создания** соответствующего файла Compose. Для первоначальной разработки Chrome удобнее запускать на Windows-хосте; перенос браузера в контейнер следует делать отдельно.

### 4. Переменные окружения

Планируемый файл `backend/.env` (пример, пароль заменить):

```dotenv
DATABASE_URL="postgresql://app_user:change_me@localhost:5432/web_performance?schema=public"
PORT=3001
FRONTEND_ORIGIN="http://localhost:5173"
MAX_CONCURRENT_AUDITS=1
ANALYSIS_TIMEOUT_MS=120000
REPORTS_DIR="./reports"
```

При наличии готовой конфигурации Prisma применить миграции и затем запустить backend и frontend в **двух терминалах**. Точные команды `npm run dev` будут заданы после создания исходников.

## Методика исследования и эксперимент

### Экспериментальная база

Разработать собственную небольшую демонстрационную страницу (например, каталог товаров) в двух контролируемых вариантах:

- **Baseline** — намеренно неоптимальная: большие изображения, избыточный JavaScript, блокирующие ресурсы.
- **Optimized** — та же страница с применёнными оптимизациями, максимально сохранёнными содержимым и функциями.

Дополнительно можно измерить несколько открытых сайтов, но для объяснения причин изменений основной материал лучше получить на контролируемых страницах.

### План измерений

1. Зафиксировать версию Chrome/Lighthouse, конфигурацию ПК и режим mobile/desktop.
2. Для каждого варианта страницы выполнить **не менее 5 измерений** в одинаковых лабораторных условиях.
3. Отдельно записать Performance Score, FCP, LCP, Speed Index, TBT, CLS; фиксировать размер основных ресурсов, если данные доступны.
4. Сравнивать **медианы** повторных измерений (а не случайный одиночный результат).
5. По возможности вводить оптимизации последовательно: **изображения → JavaScript → блокирующие ресурсы**, записывая результат после каждого этапа.
6. Проверять, что рекомендации инструмента действительно соответствуют известным проблемам тестовой страницы.
7. Описать случаи, когда метрики не улучшились или результаты колебались, вместо подгонки выводов.

**Формула для временных показателей, где меньше — лучше:**

```text
Улучшение (%) = (Медиана_до − Медиана_после) / Медиана_до × 100%
```

Для Performance Score использовать изменение **в баллах**; для CLS помимо абсолютной разницы можно вычислять относительную, только если исходное значение не равно нулю. Не смешивать измерения холодного и прогретого кеша: влияние кеширования проверять по отдельной методике.

### Критерии готовности

- Можно проанализировать как минимум один разрешённый URL через веб-интерфейс.
- API действительно запускает Lighthouse, а не возвращает заготовленные значения.
- В результатах есть реальные метрики и хотя бы **5–7 работающих правил рекомендаций**.
- История и сравнение двух запусков сохраняются после перезапуска сервера.
- Ошибки URL/тайм-аута не обрушивают приложение и отображаются пользователю.
- Есть автоматические тесты основных маршрутов и правил.
- Представлены контролируемые испытания до/после с повторениями, таблицами и выводами.
- README содержит фактически проверенную инструкцию запуска.

## Возможная структура пояснительной записки курсовой

5. **Заключение:** выполненные задачи, основные результаты, ограничения, возможные улучшения.
